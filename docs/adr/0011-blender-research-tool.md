# Blender's Python module may be used as a research-only tool, in GPL-licensed spike directories that nothing else imports

## Context and problem statement

Feature 003 imports seams and fabric regions from models exported by a modelling tool, Blender above all. Its fixtures come from the standard-library generator in `research/fixtures_gen/`, which imitates Blender's export conventions. Whether real Blender exports follow those conventions is for the spikes Q1, Q2 and Q4 to answer (003 research R6, tasks U008, U009, U011), and they need Blender itself.

Blender's Python module, `bpy` on PyPI, is GPL-3.0 [solid: the 5.2.2 package metadata says `License: GPL-3.0`]. The research lane requires spike dependencies to pass the same allowlist as the engine's (`research/AGENTS.md`), and GPL is not on it. So these spikes need either an exception or no Blender at all. This ADR is task U069 (the 003 task list, `specs/003-source-seam-import/tasks.md`, arrives with PR #107).

## Decision drivers

* Constitution IX: nothing GPL, AGPL or LGPL in the shipped artifact, and project code stays MIT OR Apache-2.0. This ADR reads IX as governing what the project ships and the code it is licensed under; a spike directory licensed GPL on its own is outside both, and nothing that ships may depend on it.
* Constitution IV: test oracles independent of the code under test. A spike that reads real Blender exports checks the generator's assumptions from outside it.
* Blender's own position that scripts using its Python API are derived works [likely: Blender's licensing FAQ]. A committed script that imports `bpy` is therefore GPL-licensed itself.
* Contributor burden: a contributor running the engine, shell or fixture gates must never need Blender.

## Considered options

* 1: allow `bpy` in research spikes only, each importing spike licensed GPL-3.0-or-later in its own directory, with nothing outside that directory importing it
* 2: no Blender at all; take the generator's conventions on trust
* 3: the maintainer runs the Blender exports by hand and commits only the measurements
* 4: relicense the project under the GPL

## Decision outcome

Chosen option: 1. It answers the spikes' questions with real Blender output, and keeps GPL code out of everything the project ships or depends on.

The rules:
* Only a spike directory under `research/` may import `bpy`. That directory carries its own `LICENSE` (GPL-3.0-or-later) and states it in its README. `bpy` is pinned (`==`) in that spike's `requirements.txt`, as the lane requires.
* Nothing in `crates/`, `bindings/`, `apps/`, `packages/`, `scripts/` or `research/fixtures_gen/` imports such a spike or `bpy`.
* No gate in `scripts/check.sh` installs or runs Blender.
* A spike's Blender exports are never committed as fixtures. Committed fixtures stay generated by `research/fixtures_gen/`, which is standard library only and byte-reproducible, because Blender's exporter output changes between versions. A spike commits its measurements, and the small inputs it needs to reproduce them, under its own directory and license.
* Files a person makes with Blender are theirs to license [solid: Blender's licensing FAQ], so a contributed CC0 model made in Blender is unaffected by this ADR. It goes in `fixtures/meshes/` under the existing contributed-model rule.

### Consequences

* Good, because the generator's Blender conventions (vertex splits at UV and normal seams, V flip, one glTF primitive per material, pole fans) are checked against Blender, not assumed.
* Good, because no shipped file, gate or engine dependency changes, so Constitution IX is unaffected.
* Bad, because the repository now holds a few GPL-licensed files. Anyone copying code from a Blender spike must honour the GPL, and the spike's README has to say so plainly.
* Bad, because spike results are tied to a Blender version, so each result names the `bpy` version it was measured with.

### Confirmation

* Review: a PR adding `import bpy` outside a spike directory with a GPL `LICENSE` is rejected.
* `cargo deny` and `scripts/check-js-licenses.sh` are unaffected, because Python spikes are outside both.
* Each Blender spike's `results.md` records the `bpy` version, as `research/AGENTS.md` already requires for library versions.

## Pros and cons of the options

### 1: allow `bpy` in GPL spike directories

* Good, because the questions get real answers, and the boundary is one directory per spike.
* Bad, because there are GPL files in the tree.

### 2: no Blender

* Good, because nothing changes.
* Bad, because the generator's imitation of Blender is never checked. A wrong assumption, such as pole fans reading as false cuts, would reach the engine's tests as a fixture that is right only by construction.

### 3: maintainer exports by hand

* Good, because no GPL file enters the tree.
* Bad, because the measurement isn't reproducible from the repository, and every re-measurement needs the maintainer.

### 4: relicense under the GPL

* Good, because no exception is needed.
* Bad, because it is a principle change for a research convenience. It would also not fix the reproducibility reason fixtures stay generated.
