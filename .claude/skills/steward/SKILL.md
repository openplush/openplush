# Driving a pull request

The binding rules are in `AGENTS.md` (Commits and PRs). This file covers how to run the loop. Each rule here exists because skipping it once cost a review run or a full-context turn.

## Reviews

- `.github/workflows/review.yml` runs when a PR opens or is marked ready, and again only when the `rereview` label is added. A push alone starts no review.
- Add `rereview` only after a run failed (a usage-limit stop, a crash) or after pushing a fix to a 🔴 finding. Never add it just to get a summary on a newer commit.
- Add `mutation-audit` (with `rereview`, or before the PR opens) when a PR adds checks to Rust code and no local mutation run covered them.
- A PR is ready to merge when CI is green on its head, a review on a recent commit found no 🔴, no 🔴 thread is open, and every 🟡 has been fixed or answered.
- Push only to fix a 🔴, a failing check, or a defect you have confirmed. Answer the other 🟡 findings in one short PR comment, and resolve their threads.
- If a finding repeats an earlier one, link to the earlier answer rather than writing the answer again.

## Local review

- Don't run `pr-reviewer`, `spec-reviewer` or `docs-reviewer` locally: the review on opening runs them, and a rerun reviews only what changed since.
- Run `mutation-auditor` once before opening a PR that adds checks to Rust under `crates/` or `bindings/` (CI runs it only on the `mutation-audit` label). Tell it not to edit tracked files while anything else runs; close each real survivor with a test and re-run that mutation to prove the test bites.
- At most two subagents at a time. A `factory` firing may run up to four through the Workflow tool, one task each in its own worktree, with nothing else running beside them.

## Stacks

- Merge a fix to a lower slice upward only after that slice merges, unless a child needs the change to build or to make sense. GitHub retargets the child when its parent merges, and merging `main` then carries every fix up in one push.
- Before every push: `git grep -n '^<<<<<<< \|^>>>>>>> '` finds nothing.
- Merge commits only, bottom-up, with the expected head SHA. Never force-push.

## Waiting

- After opening a PR, subscribe to it, so CI and review results wake you. Also schedule one safety-net check-in of about 30 minutes, for what sends no event (a conflict with `main`, another agent's push); re-arm it silently while nothing changed. Unsubscribe when the PR merges or closes, and cancel the check-in.
- Every check-in starts with the PR's `mergeable_state`. `dirty` means a conflict with `main`, and then CI and the review never start: merge `origin/main` in, resolve, push.
- Before reading CI or a review, check it is for the PR's current head SHA; an event for an older head says nothing about the new one.
- A turn that would only say "nothing new" is not worth taking. Report when a merge needs the maintainer, something is blocked, or a PR has merged.

## Pushing and posting

- Chain gates and git steps with `&&` (`scripts/check.sh engine && git commit … && git push …`), so a failing gate is never committed or pushed.
- The server appends a "Generated by Claude Code" footer to PR bodies and comments: edit it out after posting. It also escapes `>` in titles, so keep `>` out of them.
- Tick finished tasks once per session, in one PR titled `docs(tasks): tick …` that changes only checkboxes and their as-built notes. The review skips that title.

## Sessions

- One task per session, or one `factory` firing. When a task ends or the context grows long, write a short handoff for a fresh session (merged PRs, open PRs with their heads, next steps, these rules) rather than carrying on.
- Read only the files a step needs: grep `tasks.md` and the plan's ledger for the IDs in hand instead of reading them whole. Ask GitHub for one thread or the latest summary, not every thread on the PR.
- Check `main`, the open PRs and the next free slice, decision and task numbers once, at the start of a session.
